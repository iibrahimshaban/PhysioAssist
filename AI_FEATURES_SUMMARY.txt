SECTION 1: EXECUTIVE OVERVIEW
================================================================================

PhysioAssist leverages 8 major AI features to automate clinical documentation,
enhance patient engagement, and streamline administrative workflows. All AI
services are powered by multiple providers (Google Gemini, Groq, SBG) with 
seamless provider switching capabilities.

Core AI Functions:
  1. Auto-Complete (Text Suggestion)
  2. Audio Transcription (Speech-to-Text)
  3. Text Embedding (Vector Generation)
  4. Transcript Chunking (Semantic Segmentation)
  5. Documentation Generation (Clinical Note Drafting)
  6. Summarization (Session & Multi-Session Summaries)
  7. Time Parsing (Scheduling Intent Extraction)
  8. Translation (English ↔ Arabic Medical Text)

1. AUTO-COMPLETE SERVICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IT DOES:
    Provides real-time word suggestions and medical terminology auto-complete
    in both English and Arabic with category classification.

  WHY WE NEED IT:
    • Reduces data entry time and typing effort for clinicians
    • Improves consistency by suggesting standardized medical terminology
    • Enhances user experience during clinical documentation
    • Supports multi-language clinical environment

  PROBLEM IT SOLVES:
    Clinicians must quickly document patient encounters without hunting for
    correct terminology. Manual typing is slow and error-prone, especially for
    complex medical terms. Auto-complete ensures they use consistent,
    pre-validated medical vocabulary.

  TECHNICAL IMPLEMENTATION:
    • Technology: Trie (prefix tree) data structure for O(m) lookup complexity
    • Languages: English & Arabic with language detection
    • Vocabulary Source: Pre-loaded from local data files (4 vocabulary files:
      ar-general.txt, ar-medical-pt.txt, en-general.txt, en-medical-pt.txt)
    • API Endpoint: GET /api/autocomplete/suggest?prefix=...&limit=8
    • Components:
      - MultiLanguageTrieRegistry: Manages language-specific Trie instances
      - TextNormalizer: Auto-detects language from user input
      - VocabularyBootstrapService: Loads vocabulary at application startup
    
  KEY FILES:
    PhysioAssist.Api/Infrastructure/AutoComplete/
      ├── AutoCompleteController.cs
      ├── AutoCompleteService.cs
      ├── MultiLanguageTrieRegistry.cs
      ├── TextNormalizer.cs

2. AUDIO TRANSCRIPTION SERVICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IT DOES:
    Converts audio recordings of physiotherapy sessions into text transcripts
    using advanced speech recognition with medical context awareness.

  WHY WE NEED IT:
    • Eliminates manual transcription labor (hours reduced to minutes)
    • Captures complete session details without human stenographer
    • Enables downstream AI services (chunking, documentation, summarization)
    • Reduces transcription errors compared to manual methods
    • Makes sessions searchable and analyzable programmatically

  PROBLEM IT SOLVES:
    Physiotherapy sessions are audio-based. Clinicians cannot manually type
    while treating patients. Transcription requires hiring transcribers,
    introducing delays and costs. AI transcription automates this entire
    workflow while maintaining accuracy for clinical documentation.

  TECHNICAL IMPLEMENTATION:
    • Provider: Google Gemini API (multimodal)
    • Supported Formats: Multiple audio MIME types (mp3, m4a, wav, ogg, etc.)
    • Encoding: Base64 for API transmission
    • Context: System prompts guide transcription for medical accuracy
    • Integration Point: Called during Session ingestion (InitialReportModule)

3. TEXT EMBEDDING SERVICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IT DOES:
    Converts text (transcript chunks) into multi-dimensional vector embeddings
    that capture semantic meaning, enabling vector-based similarity search.

  WHY WE NEED IT:
    • Powers semantic search across patient sessions (not just keyword search)
    • Finds clinically relevant sessions even with different wording
    • Enables vector database storage for fast similarity queries
    • Foundation for machine learning and RAG (Retrieval Augmented Generation)
    • Allows "find sessions similar to patient's symptoms"

  PROBLEM IT SOLVES:
    Keyword search fails when clinical concepts are expressed differently.
    A clinician searching for "knee pain" won't find "patellofemoral pain"
    without semantic understanding. Embeddings create a semantic space where
    similar clinical concepts are close together, enabling intelligent search.

  TECHNICAL IMPLEMENTATION:
    • Provider: Google Gemini Embedding API
    • Output: Custom-dimensioned float vectors
    • Storage: SQL Server with SqlVector<float> type
    • Batch Processing: Optimized batch API for multiple chunks
    • Methods:
      - GenerateEmbeddingAsync(): Single embedding
      - GenerateEmbeddingsAsync(): Batch processing
    
  KEY FILES:
    PhysioAssist.Api/Infrastructure/Embeddding/
      └── GeminiEmbeddingService.cs

4. TRANSCRIPT CHUNKING SERVICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IT DOES:
    Intelligently segments session transcripts into semantic chunks (mini-texts),
    each representing a coherent clinical topic. Uses LLM reasoning to identify
    clinically meaningful boundaries.

  WHY WE NEED IT:
    • Raw transcripts are too long for embedding and analysis (context limits)
    • Breaks sessions into searchable, analyzable units
    • Creates natural clinical segments (e.g., "assessment of ankle" as one chunk)
    • Improves embedding quality by reducing token overhead
    • Enables targeted analysis of specific session topics

  PROBLEM IT SOLVES:
    A 30-minute session transcript may be 5000+ tokens. LLM models have context
    limits, and embedding the whole transcript loses granularity. Chunking
    creates focused, topic-specific text units that retain meaning while
    respecting system constraints. Each chunk can be independently searchable.

  TECHNICAL IMPLEMENTATION:
    • Providers: 
      - SBG (Active): Sbg API with structured JSON extraction
      - Groq (Available): Alternative provider
    • Strategy: Few-shot prompting with example chunks
    • Output: List<ExtractedChunk> with position and confidence scores
    • Prompts: [ChunkingPrompts.cs] contains few-shot examples of good chunks
    • Options: [ChunkingModelOptions.cs] for tuning model parameters
    
  KEY FILES:
    PhysioAssist.Api/Infrastructure/Chunking/
      ├── GlmChunkingService.cs (Groq)
      ├── Sbg/SbgChunkingService.cs (Active)
      ├── ChunkingModelOptions.cs
      ├── ChunkingPrompts.cs
      └── ExtractedChunkPromptSchemaBuilder.cs

5. DOCUMENTATION GENERATION SERVICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IT DOES:
    Automatically generates clinical documentation from transcripts, including:
    • SOAP Note narrative (Subjective, Objective findings, Assessment, Plan)
    • Structured objective findings in JSON
    • Professional-grade documentation ready for patient records

  WHY WE NEED IT:
    • Eliminates manual documentation work (1-2 hours per session reduced to
      seconds via AI, then 5-10 minutes for clinician review/approval)
    • Ensures consistent documentation standards across therapists
    • Reduces liability risk via standardized, complete records
    • Enables compliance with medical record requirements
    • Integrates findings into EHR seamlessly

  PROBLEM IT SOLVES:
    Clinical documentation is the most time-consuming part of physiotherapy.
    Clinicians must remember session details, type clinical assessments,
    and format notes correctly. Post-session documentation takes 1-2 hours.
    AI generation creates a draft (90% complete) in seconds; clinician reviews
    and approves, reducing time to minutes. This reduces burnout and improves
    clinician availability for actual patient care.

  TECHNICAL IMPLEMENTATION:
    • Providers: 
      - SBG (Active): Primary provider
      - Groq (Available): Legacy alternative
    • Input: Transcript text (usually pre-chunked)
    • Output: NarrativeDraftResult with:
      - Subjective: Patient's complaint and history
      - Assessment: Clinical interpretation
      - Plan: Treatment recommendations
      - Objective Findings: Structured JSON (measurements, observations)
    • Prompts: [DocumnetationSystemPrompts.cs] with clinical guidelines
    • Options: [DocumentationChatOptions.cs] for model tuning
    • Quality: Few-shot examples ensure professional output

  6C. ROLLUP SUMMARIZATION SERVICE (Multi-Session)
  ─────────────────────────────────────────────────

  WHAT IT DOES:
    Creates case-level summaries spanning multiple sessions, with filtering
    options for specific clinical focuses and audience-aware output (doctor
    vs. patient versions).

  WHY WE NEED IT:
    • Tracks patient progress over weeks/months of treatment
    • Enables clinical decision-making for major treatment adjustments
    • Supports insurance authorization requests (summary of treatment course)
    • Creates discharge summaries when treatment ends
    • Supports handoff to other providers

  PROBLEM IT SOLVES:
    A patient may have 20+ sessions over 2 months. Understanding overall
    progress, which interventions worked, and current status requires reading
    all notes (1+ hour). Rollup summaries synthesize the entire course of
    care into a single document, enabling strategic decisions about
    treatment continuation or modification.

  TECHNICAL IMPLEMENTATION:
    • Provider: SBG API with filtering and scope parameters
    • Input: Multiple session summaries or full transcripts
    • Scope Options: Filter by treatment focus (e.g., "knee" only)
    • Audience Options: Separate professional (doctor) and patient versions
    • Output: Comprehensive case summary with progress assessment
    
  KEY FILES:

7. TIME PREFERENCE PARSER (Scheduling)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IT DOES:
    Converts natural language patient availability statements into structured
    scheduling data (dates, times, recurring patterns) for appointment booking.

  WHY WE NEED IT:
    • Eliminates manual data entry during intake/scheduling
    • Handles complex scheduling preferences (e.g., "Mondays and Thursdays
      after 5pm except the 2nd week of the month")
    • Reduces scheduling booking errors
    • Improves scheduling efficiency for clinics with high patient volumes
    • Integrates directly with scheduling module

  PROBLEM IT SOLVES:
    Patients express availability in natural language during intake or when
    contacting the clinic: "I can come Tuesday or Friday mornings, but I have
    to pick up my kids at 3pm." Manually converting this to structured
    scheduling fields is error-prone and slow. AI parsing converts natural
    language directly into structured availability slots, eliminating manual
    transcription and enabling immediate scheduling.

  TECHNICAL IMPLEMENTATION:
    • Providers:
      - SBG (Active): Primary implementation
      - Groq (Legacy): Available alternative
    • Input: Free-text patient availability statement
    • Output: PatientTimePreferenceDto with:
      - Preferred dates
      - Available time ranges
      - Recurring patterns (weekly, bi-weekly, etc.)
      - Timezone: Egypt (UTC+3)
    • Prompts: [TimePreferenceExtractionPrompts.cs] with structured format
    • Options: [TimeParserChatOptions.cs] for model configuration
    • Used By: PatientModule (intake), SchedulingModule (appointment booking)
    
  KEY FILES:
    PhysioAssist.Api/Infrastructure/TimeParser/
      ├── GroqTimePreferenceParser.cs (Legacy)

8. TRANSLATION SERVICE (English ↔ Arabic)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IT DOES:
    Translates clinical answers and documentation from English to Arabic,
    preserving medical terminology and clinical accuracy. Also supports
    reverse translation (Arabic → English).

  WHY WE NEED IT:
    • Serves Arabic-speaking patients in a multi-lingual environment
    • Ensures clinical accuracy (not just literal translation) for medical terms
    • Enables Arabic patients to receive care instructions and summaries in
      their native language
    • Improves patient compliance by using familiar language
    • Required for compliance in Arabic-speaking regions (Egypt, MENA)

  PROBLEM IT SOLVES:
    Direct translation engines produce poor medical translations. A clinical
    term like "dorsiflexion" needs precise medical terminology in Arabic, not
    literal word-for-word translation. Specialized translation ensures:
    - Medical accuracy (terms are clinically correct in Arabic)
    - Consistency (same English term always maps to same Arabic term)
    - Cultural appropriateness (medical concepts adapted for MENA context)
    - Patient safety (wrong translation could compromise care)

  TECHNICAL IMPLEMENTATION:
    • Providers:
      - SBG (Active): Primary implementation
      - Nvidia (Legacy): Available alternative
    • Input: English clinical text or answers
    • Output: Arabic translation with medical terminology preserved
    • System Prompts: [TranslationSystemPrompts.cs] with medical glossary
    • Options: [TranslationChatOptions.cs] for model tuning
    • Used By: QueryModule (on-demand answer translation)
    • Integration: AnswerTranslationPlugin provides plugin-based translation
    
  KEY FILES:
    PhysioAssist.Api/Infrastructure/Translation/
      ├── NvidiaAnswerTranslationService.cs (Legacy)
      ├── Sbg/SbgAnswerTranslationService.cs (Active)
      ├── TranslationChatOptions.cs

SECTION 3: HOW MODULES USE AI FEATURES
================================================================================

╔════════════════════════════════════════════════════════════════════════════╗
║                      MODULE → AI SERVICES MAPPING                         ║
╚════════════════════════════════════════════════════════════════════════════╝

SESSION MODULE
─────────────
  AI Services Used: Transcription, Chunking, Embedding
  Purpose: Ingest and process therapy session recordings
  Workflow:
    1. User uploads session audio file
    2. Transcription Service converts audio → text transcript
    3. Chunking Service segments transcript into semantic chunks
    4. Embedding Service converts each chunk → vector embedding
    5. Chunks and embeddings stored in database for future search
  Benefit: Enables semantic search across all patient sessions

DOCUMENTATION MODULE
────────────────────
  AI Services Used: Documentation Extraction, Session Summarization, 
                    Rollup Summarization
  Purpose: Generate and organize clinical documentation
  Workflow:
    1. Documentation Extraction creates SOAP notes from transcript
    2. Session Summarization creates concise 1-session summaries
    3. Rollup Summarization creates multi-session case summaries
  Output: Professional clinical records ready for patient charts and EHR
  Benefit: Reduces documentation time from 1-2 hours to minutes of review

INITIAL REPORT MODULE
─────────────────────
  AI Services Used: Transcription, Patient Summary
  Purpose: Create initial patient intake reports
  Workflow:
    1. Clinician conducts initial assessment (audio recorded)
    2. Transcription Service converts assessment → text
    3. Patient Summary creates patient-friendly summary of findings
    4. Report assembled with patient demographics, assessment, and summary
  Benefit: Automated intake documentation reduces clinician paperwork

PATIENT MODULE
──────────────
  AI Services Used: Time Preference Parser, (optionally) Auto-Complete
  Purpose: Manage patient demographics and scheduling preferences
  Workflow:
    1. During intake, capture patient availability in free-text format
    2. Time Preference Parser converts → structured scheduling slots
    3. Slots stored for use in appointment booking
  Benefit: Eliminates manual transcription of scheduling preferences

QUERY MODULE
────────────
  AI Services Used: Translation Service (via AnswerTranslationPlugin)
  Purpose: Translate clinical information for multi-lingual support
  Workflow:
    1. Clinical answer generated in English
    2. Translation Service translates → Arabic on-demand
    3. Translated answer returned to Arabic-speaking user
  Benefit: Seamless multi-lingual clinical information delivery

SCHEDULING MODULE
──────────────────
  AI Services Used: Time Preference Parser
  Purpose: Book appointments respecting patient preferences
  Workflow:
    1. Patient availability parsed into structured format (Time Parser)
    2. Available time slots compared against clinician schedules
    3. Appointments booked into mutually available slots
  Benefit: Automated scheduling respecting complex patient preferences

SECTION 4: AI PROVIDER ARCHITECTURE
================================================================================

PhysioAssist uses a MULTI-PROVIDER STRATEGY enabling cost optimization and
provider failover:

ACTIVE PROVIDERS (Currently in Use)
───────────────────────────────────
  • SBG (SBG Model)
    - Used For: Documentation, Chunking, Time Parsing, Translation
    - Cost: Likely low-cost alternative
    - Quality: Good results at scale
  
  • Google Gemini
    - Used For: Audio Transcription, Embeddings
    - Quality: Industry-leading multimodal (audio+image) support
    - Reliability: Highly available

  • Groq
    - Used For: Patient Summary
    - Speed: Known for fast inference
    - Cost: Variable pricing model

ALTERNATIVE PROVIDERS (Available for Switching)
────────────────────────────────────────────────
  • Groq
    - Complete legacy implementation for: Documentation, Chunking, Time Parsing
    - Can be switched in DependancyInjection.cs if needed
  
  • Nvidia
    - Legacy translation service
    - Available as fallback if SBG translation fails

PROVIDER SWITCHING
──────────────────
All providers are swapped via DependancyInjection.cs, allowing:
  • Cost optimization (switch to cheaper provider if quality acceptable)
  • Provider failover (switch if primary provider is down)
  • A/B testing (compare outputs between providers)
  • Performance tuning (switch to faster provider)

Session Ingestion Flow:
  Audio File
    ↓
  [Transcription Service] → Text Transcript
    ↓
  [Chunking Service] → Semantic Chunks
    ↓
  [Embedding Service] → Vector Embeddings
    ↓
  Database Storage (Chunks + Embeddings)
    ↓
  Searchable via [SessionChunkSearchService]

  Transcript/Chunks
    ↓
  [Documentation Extraction] → SOAP Notes + Objective Findings
    ↓
  [Session Summarization] → Concise Session Summary
    ↓
  [Patient Summary] → Plain-Language Patient Summary
    ↓
  Multi-Session:
    [Rollup Summarization] → Case-Level Summary


Scheduling Flow:
  Patient Availability (Free-Text)
    ↓
  [Time Preference Parser] → Structured Availability Slots
    ↓
  [Scheduling Module] → Appointment Booking
    ↓
  Confirmed Appointment


Multi-Lingual Support:
  English Clinical Content
    ↓
  [Translation Service] → Arabic Medical Translation
    ↓
  Bilingual Patient Records

SECTION 8: CONFIGURATION & DEPENDENCY INJECTION
================================================================================

All AI services are configured in: PhysioAssist.Api/DependancyInjection.cs

Extension Methods for AI Configuration:
  
  AddDocumentationSummarizationConfig()
    - Registers: IDocumentationExtractionService, ISessionSummarizationService,
                 IRollupSummarizationService
    - Configures: SBG API endpoints and options
  
  AddPatientSummaryConfig()
    - Registers: IPatientSummaryAiService
    - Provider: Groq with reasoning capabilities
  
  AddPatientTimePrefernceParser()
    - Registers: IPatientTimePreferenceParser
    - Provider: SBG with scheduling domain expertise
  
  AddTranslationServices()
    - Registers: IAnswerTranslationService
    - Provider: SBG (Primary) or Nvidia (Fallback)
  
  AddAutoCompleteService()
    - Registers: IAutoCompleteService
    - Data Source: Local vocabulary files
  
  AddEmbeddingConfig()
    - Registers: IEmbeddingService, ITranscriptChunkingService
    - Embedding Provider: Google Gemini
    - Chunking Provider: SBG
  
  AddAudioTranscriptionConfig()
    - Registers: IAudioTranscriptionService
    - Provider: Google Gemini (multimodal)
